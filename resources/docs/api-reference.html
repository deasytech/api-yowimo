API REFERENCE · V1

Build on Yowimo

Everything the client app needs to authenticate players, run the game engine, move tokens, and keep a party in sync — verified directly against the current backend, endpoint by endpoint.

Authentication

Every endpoint except GET /health requires a Clerk session JWT as a bearer token. There is no separate API key.

Header
Authorization: Bearer <clerk_session_jwt>

Missing or invalid tokens return 401 before any route logic runs. There's no refresh endpoint in this API — token lifecycle is owned by Clerk on the client.

Response format

Every response, success or failure, is wrapped the same way:

Success
{
  "success": true,
  "message": "...",
  "data": { ... }
}
Error
{
  "success": false,
  "message": "...",
  "errors": { ... }
}

Always check success, not just the status code, when parsing a response body.

Pagination

List endpoints are cursor-paginated only — there is no page-number parameter anywhere in this API.

ParamMeaning
per_pagePage size. Default 20, max 50 (server clamps silently).
cursorOpaque string from meta.next_cursor / meta.prev_cursor. Pass it back verbatim.
meta on a paginated list
{
  "per_page": 20,
  "has_more_pages": true,
  "next_cursor": "eyJ...==",
  "prev_cursor": null
}
ExceptionGET /friends and GET /friend-requests return the full collection with no meta block at all — don't build cursor UI for those two.

Rate limits

A global limiter applies everywhere; some write actions stack a tighter, purpose-specific limiter on top. Exceeding either returns 429.

LimiterLimitApplies to
api60 / minEvery request (default)
purchases10 / minPack & token-bundle purchase, payment method default/delete
party-actions30 / minLike, join, leave, start, end, game actions (turns, votes, pause/resume)
friend-requests20 / minAll friend-request, friend & block mutations
push-tokens10 / minRegister / unregister device
reactions30 / minGame emoji reactions
account-deletion3 / minDelete account

All limiters key by authenticated user id (falling back to IP where unauthenticated).

Errors

Status codes are consistent across the whole API — the same exception type always produces the same code.

CodeMeaning
401Missing, malformed, or expired bearer token.
403Authenticated, but not allowed to perform this action on this resource (e.g. non-host trying to start a party's game).
404Resource doesn't exist — or, for privacy, exists but isn't yours to see (used instead of 403 where existence itself shouldn't leak).
409Conflict with current state (already purchased, party full, duplicate friend request).
422Validation failed, or the action is invalid for the resource's current state (a Laravel-style state-machine violation, e.g. ending a party that isn't live).
429Rate limit exceeded.
500Unexpected server error.
502An upstream provider failed (currently only Clerk during account deletion). Nothing was changed — safe to retry.

DELETE/users/me

Permanently close the authenticated player's account.

Rate limit account-deletion (3/min)

Deletes the player's Clerk account first, then soft-deletes the local account. If Clerk can't be reached or rejects the call, nothing changes and the request returns 502 — safe to retry.

Side effects

  • Hosted parties: draft/scheduled become cancelled; live ones become ended.
  • Leaves every party the player joined (other members get the usual party.member.left event).
  • Friendships and pending requests are closed; the push token is removed.
  • Wallet, ledger, purchase, and gameplay history are kept.
Sign the user outThe bearer token stops working immediately (401 on the next request). Clear the Clerk session on the device after a 200.
200 OK401429502 Clerk unavailable
Shape

POST/token-bundles/{id}/purchase

Charge the player and credit tokens to their wallet, via Paystack.

Rate limit purchases (10/min)

Headers

HeaderRules
Idempotency-Keyrequiredsame mechanism as pack purchase

Body

FieldRules
payment_referenceoptional, string — a reference from a charge already completed via the Paystack mobile SDK (card details never pass through our API). Verified server-to-server before anything is credited.
payment_method_idoptional, integer — charge a previously saved card instead (see Payment Methods below). Must belong to the caller.

Business rules

  • Give at most one of payment_reference / payment_method_id. Give neither to charge the caller's default saved card.

  • Card/payment declined, or no payment method available at all → 402.
  • Same idempotency key reused for a different bundle → 409.
No live gateway configured yet in some environmentsUntil the backend has a live Paystack secret key, this falls back to a manual/test driver that always approves and never saves a card — same request/response shape either way, so build against this doc regardless of which is currently active.

Game Sessions

Runs inside a live party: turn order, cards, timers, voting and results. Server-authoritative — clients send actions, the server decides outcomes and broadcasts them.

Game flow

A session moves through these statuses:

  • running → the current player completes or skips their turn, the host advances it, or the turn times out.
  • paused ↔ running — host only; the turn timer is frozen and no turn actions or votes are accepted.
  • voting — after the last turn of the last round, a 30-second window to vote (including on the final turn).
  • completed — the voting window closed; completion rewards, MVP, badges and the AI recap follow.
  • ended — the host ended the party before the game finished. XP already earned is kept, but there are no completion rewards.

Turn rules the client should expect:

  • Turn order is randomized once at start. Players who leave are skipped automatically (if it was their turn, it's closed as skipped); players who join mid-game are added to the end of the order. Use active_player_ids to render who's still playing.
  • A skipped or timed-out turn earns no challenge XP and can't be voted on.
  • Every turn carries a server deadline (expires_at). Render the countdown from it rather than starting a local timer.

Realtime events

Subscribe to private-game-session.{gameSessionId} (party members) for the game, and to presence-party.{partyId} for the lobby. Events use custom names, so with Laravel Echo listen with a leading dot, e.g. .listen('.turn.started', ...). A player in the lobby learns about a new game from game.started on the party channel, or by calling GET /parties/{party}/game on (re)load — that covers late joiners, reopened apps, and the host returning to the lobby. Connecting

  • Server: Laravel Reverb, which speaks the Pusher protocol — use laravel-echo + pusher-js (pusher-js/react-native on mobile). Connection values come from the backend's REVERB_APP_KEY, REVERB_HOST, REVERB_PORT, REVERB_SCHEME for each environment.
  • Auth endpoint: POST {API origin}/broadcasting/auth — at the site root, not under /api/v1. Send the same Clerk Authorization: Bearer token as the REST API, with body { socket_id, channel_name }. It returns the signature Pusher needs; 403 means you're not allowed on that channel.
  • Channel names: in Echo, echo.private('game-session.77') and echo.join('party.902') — Echo adds the private- / presence- prefixes itself. Your own notifications arrive on echo.private('App.Models.User.{yourUserId}').
  • Who can subscribe: party.{id} and game-session.{id} — anyone who has joined that party (including players who left, so they still see the game end). App.Models.User.{id} — only that user.
  • After reconnecting: events sent while you were offline aren't replayed. Refetch GET /game/{gameSession} (and GET /parties/{party}/game if you don't know the id) whenever the socket reconnects or the app returns to the foreground.

// backend team (REVERB_APP_KEY / REVERB_HOST / REVERB_PORT / REVERB_SCHEME).
// The app key is public; never ship REVERB_APP_SECRET.
const echo = new Echo({
  broadcaster: 'reverb',
  Pusher,
  key: REVERB_APP_KEY,
  wsHost: REVERB_HOST,
  wsPort: REVERB_PORT,
  wssPort: REVERB_PORT,
  forceTLS: REVERB_SCHEME === 'https',
  enabledTransports: ['ws', 'wss'],
  // Private/presence channels are authorized by the API. Clerk session
  // tokens are short-lived, so fetch a fresh one per subscription rather
  // than setting a fixed Authorization header once at connect time.
  authorizer: (channel) => ({
    authorize: async (socketId, callback) => {
      try {
        const token = await getToken(); // Clerk
        const res = await fetch(`${API_ORIGIN}/broadcasting/auth`, {
          method: 'POST',
          headers: {
            Authorization: `Bearer ${token}`,
            'Content-Type': 'application/json',
            Accept: 'application/json',
          },
          body: JSON.stringify({ socket_id: socketId, channel_name: channel.name }),
        });
        if (!res.ok) throw new Error(`Channel auth failed: ${res.status}`);
        callback(null, await res.json());
      } catch (error) {
        callback(error, null);
      }
    },
  }),
});
